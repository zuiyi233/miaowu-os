# 多用户设置页与公共技能库排查结论（2026-05-29）

## 1. 背景

本次排查针对设置页中的以下能力：

- AI 供应商
- 草稿
- 记忆
- 工具
- 技能

排查目标有两个：

1. 先确认当前代码里哪些页面仍带有明显的单用户遗留设计。
2. 明确多用户模式下这些页面各自应该归属到“用户隔离配置”还是“系统公共配置”。

本结论基于 2026-05-29 的只读代码排查，未做浏览器运行态抓包，因此：

- 能确认的是代码链路和存储边界。
- 不能在本文中直接声称所有页面都已运行态复现。

---

## 2. 当前代码现状

### 2.1 旧版本地实例更可能对应 `D:\miaowu-os\deer-flow-main`

当前用户截图和前面对话，更像是旧版本地实例，而不是 `N:\miaowu-os-merge-upstream-main` 中的新版设置页。

这套旧版设置页实际只有：

- Appearance
- Notification
- Memory
- Tools
- Skills
- About

它**没有**：

- AI 供应商页
- 草稿页

旧版代码里的几个关键事实：

1. `frontend/next.config.js` 的 gateway fallback 仍默认指向 `127.0.0.1:8001`，与本项目 local-dev 应固定走 `127.0.0.1:8551` 的约束冲突。
2. `skills` 页通过裸 `fetch(${getBackendBaseURL()}/api/skills)` 直接请求。
3. `tools` 页通过裸 `fetch(${getBackendBaseURL()}/api/mcp/config)` 直接请求。
4. `memory` 页通过裸 `fetch(${getBackendBaseURL()}/api/memory)` 直接请求。

这意味着旧版本地实例里：

- `技能` 页已确认存在同类风险。
- `工具` 页高度同类。
- `记忆` 页也存在同类接口链路风险，但具体表现不一定是相同空白态。

### 2.2 新版合并代码位于 `N:\miaowu-os-merge-upstream-main\deer-flow-main`

新版设置页已经扩展为：

- Account
- Appearance
- AI 供应商
- Notification
- 草稿
- Memory
- Tools
- Skills
- Admin
- About

新版里这几页的现状如下：

#### AI 供应商

- 已改为走 `/api/user/ai-settings` 和 `/api/user/newapi-sync/groups` 这类用户级接口。
- 但“读取”链路仍有部分使用原生 `fetch(..., { credentials: "include" })`。
- “保存/提交”链路已改为统一 `fetchWithAuth`。

结论：

- 比旧版已经好很多。
- 但“读取阶段仍带有旧风格实现”，还不算完全收口。

#### 草稿

- 当前草稿设置页只是一个“默认保留时长”选择器。
- 它通过 `useLocalSettings()` 读写前端本地设置。
- 当前底层存储是浏览器 `localStorage`，键名为 `deerflow.local-settings`。

结论：

- 它不是旧版那种“请求错误实例导致空页”的同类问题。
- 但它是典型的“单浏览器单用户假设”遗留设计。

#### 记忆

- 新版 `memory` API 已改成统一 `authFetch`。
- 读写链路都走 `/api/memory`，不再是旧版裸 `fetch` 风格。

结论：

- 不属于旧版技能页那种前端接口链路问题。
- 但多用户前提下仍要继续保证服务端按登录用户严格隔离。

#### 工具

- 新版 `MCP` 配置已走统一 `fetcher`。
- `Feature Flags` 也走统一 `fetcher`。
- 但它们当前表达的仍是“系统级能力配置”，不是天然的“用户级偏好设置”。

结论：

- 不属于旧版技能页那种同类请求问题。
- 但从产品边界上看，它仍需要拆清“系统公共配置”和“用户启用状态”。

#### 技能

- 新版技能 API 已走统一 `fetcher`。
- 但技能页仍保留“安装技能”这类能力入口，而这与当前产品策略冲突。

结论：

- 它在新版里已不再是旧版那种裸请求问题。
- 但从多用户产品规则看，当前能力模型仍未完全对齐。

## 3. 单用户遗留设计的核心问题

### 3.1 本地设置直接落在浏览器 `localStorage`

当前 `DraftSettingsPage` 使用的 `useLocalSettings()` 底层落在：

- `deerflow.local-settings`
- `deerflow.thread-model.<threadId>`

这类存储有一个明显前提：

- 同一个浏览器环境默认只服务一个用户，或者默认不在意不同账号之间的设置串用。

对于多用户系统，这个前提不成立。只要两个账号在同一浏览器 profile 下登录切换，就可能出现：

- 草稿保留时长串用
- 模型偏好串用
- 线程模型偏好串用
- 本地通知类偏好串用

### 3.2 系统公共目录与用户启用状态未彻底分离

当前 `技能` 和 `工具` 都还有类似问题：

- 目录本身更像“系统公共注册表”
- 但设置页又直接把它暴露成“当前用户可编辑的个人配置”

多用户下这两层必须拆开：

1. 系统公共目录
2. 用户个人启用状态

否则会出现：

- 某个用户关闭后影响其他用户
- 某个用户安装/删除后污染整个系统
- 数据隔离与能力隔离混在一起，无法审计

### 3.3 普通用户不应拥有“安装技能”能力

当前产品规则已经明确：

- 不允许用户安装技能
- 系统只维护一个公共技能库
- 用户只能决定自己是否启用某个公共技能

这意味着：

- “安装技能”不是用户设置能力
- 它要么完全去掉
- 要么只保留给管理员/部署者

## 4. 多用户模式下的目标边界

下面是推荐的最终边界。

| 页面/能力 | 归属 | 普通用户是否可改 | 目标说明 |
| --- | --- | --- | --- |
| AI 供应商 | 用户级 | 是 | 每个用户维护自己的 provider、key、model routing，不允许跨用户混用 |
| 草稿保留时长 | 用户级 | 是 | 不能再只存在浏览器全局 localStorage，至少要做到按用户隔离 |
| 草稿数据 | 线程/用户级 | 是 | 草稿图片、音频、挂载动作必须绑定 thread 与 user |
| 记忆 | 用户级 | 是 | 主记忆必须按登录用户隔离，不能混用 |
| 工具目录（MCP servers） | 系统级/管理员级 | 否 | 工具注册表是公共资源，应由系统或管理员维护 |
| 工具启用状态 | 用户级或角色级 | 视策略而定 | 如果允许用户选择工具，则只应记录“我是否启用某公共工具” |
| Feature Flags | 系统级/管理员级 | 否 | 这是系统行为开关，不应该放在普通用户的个人设置语义里 |
| 技能目录 | 系统级/管理员级 | 否 | 只有一个公共技能库，不允许普通用户安装 |
| 技能启用状态 | 用户级 | 是 | 用户只控制自己是否启用某个公共技能 |
| 技能安装 | 系统级/管理员级 | 否 | 普通用户禁止安装，最好前后端都封死 |

## 5. 对当前产品规则的直接落地解释

### 5.1 技能的正确模型

技能必须拆成两层：

1. **公共技能库**
   - 由系统维护
   - 所有用户看到的是同一份目录
   - 普通用户不能安装、删除、改写

2. **用户启用状态**
   - 记录某个用户是否启用某个公共技能
   - 例如：`user_id + skill_name + enabled`
   - 用户只影响自己，不影响别人

这也是当前技能页最需要收口的产品方向。

### 5.2 工具的正确模型

工具页不能继续把“系统注册表”和“个人选择”混成一个页的一个数据结构。

比较合理的拆法是：

1. **公共工具注册表**
   - 系统级
   - 管理员维护
   - 例如 MCP server 列表、可用 feature modules

2. **用户工具偏好**
   - 如果产品允许用户控制自己是否启用某公共工具，则单独存用户偏好
   - 如果不允许用户控制，则工具页应改成只读，或直接移到管理员设置

### 5.3 AI 供应商的正确模型

AI 供应商必须是彻底的用户级配置：

- key 不共享
- default provider 不共享
- feature routing 不共享
- model group 映射不共享

新版 `/api/user/ai-settings` 的方向是对的，但仍要继续清理残余单用户实现习惯。

### 5.4 草稿的正确模型

草稿要分开看：

1. **草稿数据本身**
   - 必须按线程/用户隔离
   - 不能混用

2. **草稿默认保留策略**
   - 如果只是浏览器临时偏好，可以继续本地存储，但这不满足“账号级隔离”
   - 如果产品要求严格多用户隔离，则它也应移到服务端用户设置表

因此，从你当前给出的产品要求看，草稿默认保留时长也不应再继续只放在公共 `localStorage`。

### 5.5 记忆的正确模型

记忆必须保持用户级隔离，不允许混用。

这里还要继续坚持一个边界：

- 主 memory 保存用户长期偏好和长期上下文
- 小说作品事实、章节状态、角色状态不要直接混进主用户记忆
- 小说侧作品事实应留在项目/作品级上下文系统中

这样才能同时做到：

- 用户隔离
- 作品隔离
- 长期偏好与临时作品事实分层

## 6. 当前可直接执行的改造方向

建议按下面顺序推进。

### 第一阶段：先把边界定死

1. 技能页移除普通用户“安装技能”入口。
2. 技能接口改成“公共目录 + 用户启用状态”两层模型。
3. 工具页区分“公共工具注册表”和“个人启用状态”。
4. Feature Flags 从普通用户设置中剥离到管理员设置。

### 第二阶段：把残余单用户前端存储迁到用户隔离模型

1. 草稿保留时长从 `localStorage` 迁到用户设置。
2. 线程模型偏好、模型偏好等与账号相关的设置也评估是否迁到用户级存储。
3. 明确哪些设置允许“同浏览器不同账号共享”，哪些绝不允许共享。

### 第三阶段：统一旧版/新版链路

1. 旧版本地实例涉及 settings 的 `8001` fallback 清理到 `8551`。
2. 旧版 `skills / tools / memory` 裸请求链路统一收口。
3. 新版 `AI 供应商` 的读取链路也统一到认证封装。

---

## 7. 当前结论

可以直接定性为：

1. 这些页面和能力原先确实带有明显的单用户开发前提。
2. 切到多用户后，不能继续混用“公共目录”和“用户启用状态”。
3. `技能` 是最明确的一类：
   - 只有公共技能库
   - 普通用户不能安装
   - 用户只能启用/停用公共技能
4. `工具` 基本也应该按同样思路拆成“系统公共注册表”与“用户个人启用状态”。
5. `AI 供应商 / 记忆 / 草稿默认策略` 则都应该落到用户级隔离模型，而不是继续依赖单浏览器本地状态。

---

## 8. 本文后续用途

后续如果继续推进这一块，应以本文为准，优先避免以下错误方向：

- 继续把技能安装暴露给普通用户
- 继续把 MCP/工具注册表当成普通用户个人设置
- 继续把账号相关偏好只存在浏览器全局 localStorage
- 把作品级事实直接并入主用户 memory

如果后续开始实施代码改造，建议先以“技能页 + 工具页 + 草稿用户设置迁移”作为第一批收口对象。
